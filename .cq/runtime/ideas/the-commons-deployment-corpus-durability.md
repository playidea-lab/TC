## 왜 이 사이클인가

서비스 가용성 BLOCKING #4(배포 타깃) + 사용자의 근본 질문("지식을 쌓는
구조에서 지식은 어디에 쌓이나")이 한 결정으로 수렴했다: 내구 SoT가 PG
자체인가, 이식 가능한 정전 저장소 위의 projection인가. 이게 배포·백업·
federation·거버넌스 신뢰성을 전부 가른다.

## 결정화한 설계 (Canonical) — A+

> 정전(canonical)인 것은 PG가 아니라 **content-hash 주소화된 L1 evidence**
> 다. PG는 오늘 그것을 담는 serving/index 계층일 뿐. 따라서 Phase-1은
> 단일 전용 managed PG로 출하하되, 코퍼스의 *이식성*을 릴리스 불변식으로
> 박아 거버넌스 약속("PI Lab 사유 아님 / 운영자보다 오래 산다")을
> 구조적으로 참이게 한다. 풀 C(객체스토어 이중쓰기)는 무손실 v0.2
> 업그레이드로 미룬다.

## 확정 결정

### DD1. SoT 모델 = A+ (단일 PG + 검증된 이식성), B·C 기각

- **B(Supabase 재사용) 1차원리 기각**: cq c4와 동일 blast radius —
  마이그레이션·쿼터 사고 하나가 press(cq)와 library(TC)를 동시에 죽인다.
  자산인 코퍼스를 cq 운영 DB에 결합 = soul.md 리뷰 1순위(데이터 무결성/
  장애 복구)에서 최악. 레이어 흐림(ID1)은 부차적 이유.
- **C(객체=정전) v0.2로 연기**: 진짜 비용은 이중쓰기 코드가 아니라
  객체↔PG 일관성·부분실패 rehydrate(분산 복잡도). 소비자 1개 Phase-1엔
  조숙 — federation이 v0.2이므로(비전 카드 + 이번 사이클 확인) C는 v0.2
  문제를 v0.1 비용으로 푸는 것.
- **A+ 채택**: A를 정밀화 — 거버넌스는 *검증된 이식성*으로 담보.

### DD2. L1 정체성 = content hash (PG row id 아님)

`compute_content_hash`(이미 존재)가 L1 레코드의 정체성. PG는 그 바이트를
담는 매체이지 정체성의 근원이 아니다. 이게 이식성·재현성의 토대.

### DD3. 거버넌스 = "한 번 테스트"가 아니라 릴리스 불변식

A의 export 약속은 drift/rot하면 무너진다. 따라서:

1. `corpus export` — canonical L1 바이트의 자기완결 덤프
2. round-trip(export → 빈 PG → re-import → hash 동일) = **릴리스 게이트**
   (CI/finish에서 강제, 일회성 금지)
3. 그 덤프를 PG 호스트와 **독립된 offsite**에 백업
4. PG는 managed **PITR** 2차 방어 (export 간격 사이 델타 손실 완화)

→ 덤프 가진 누구나 Commons 기동 가능 = "운영자보다 오래/사유 아님"이
구조적으로 참. C는 덤프를 라이브 객체-SoT로 승격하는 무손실 업그레이드.

### DD4. 배포 토폴로지 (DD1~DD3에서 따라 나옴)

- **disposable TC 컨테이너** (fly app — PI Lab 기존 fly.io 인프라, cq
  사설망 뒤 internal-only)
- **전용 managed PostgreSQL+pgvector** (Supabase 아님 — DD1 blast radius),
  PITR 활성
- **ingest량 연동 corpus-export → offsite 객체 스토리지**
- 컨테이너는 cattle, **DB·덤프가 자산(pet)**

## 요구사항 (EARS)

- **DC1** WHEN evidence가 ingest될 때, L1 레코드는 content hash로 주소화
  되어 PG row id와 독립적으로 식별 가능해야 한다.
- **DC2** WHERE 코퍼스 보존이 필요할 때, `corpus export`는 PG 없이도
  L1 전체를 재구성 가능한 자기완결 덤프를 생성한다.
- **DC3** WHILE 릴리스가 진행될 때, export→빈 PG→re-import→hash 동일
  round-trip이 게이트로 강제된다 (실패 시 릴리스 차단).
- **DC4** WHEN corpus-export가 수행될 때, 덤프는 PG 호스트와 독립된
  offsite에 저장된다.
- **DC5** IF PG가 export 간격 사이 파국 손실될 때, managed PITR로 델타를
  복구한다 (단일점 아님, 다층 방어).
- **DC6** WHERE TC가 배포될 때, 컨테이너는 무상태 disposable이고 cq
  사설망 뒤 internal-only이며, 코퍼스 PG는 cq 운영 DB와 분리된다.

## 탐구 중 인사이트

1. 두 질문(배포·지식 위치)은 한 결정으로 수렴 — disposable vs asset.
2. B는 선호가 아니라 1차원리(blast radius)로 탈락.
3. C의 비용은 코드가 아니라 분산 일관성 — federation 없으면 조숙.
4. 거버넌스를 떠받치는 건 storage 토폴로지가 아니라 *검증된 이식성*.
   "운영자보다 오래"는 정책 문구가 아니라 round-trip 불변식으로 참이 된다.
