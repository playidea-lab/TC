# TC MCP — LLM agent용 추천·환류·적재 인터페이스

> 폐루프 주체인 LLM agent(Claude Code)가 TC를 텍스트 CLI 파싱 없이 MCP 도구로 직접 쓰고, 추천(next_config)·실행·환류·적재가 한 줄로 이어지게 한다.

## 왜 이 아이디어인가

오늘 codegen 키 LLM 경로를 제거하고 `/loop`·`/goal` + `cq_dispatch`로 폐루프를 재구성했다(코드 생성 주체 = Claude Code). 그런데 코드 리뷰 결과 사이클의 연결고리가 끊겨 있었다:

- recommend가 주는 `next_config`가 `cq_dispatch run`에 인자가 없어 **버려진다**.
- PCQ `config = {recipe_id}`뿐이라 hyperparam이 코드 본문에 갇히고 infogain within-recipe·중복 회피 가드가 헛돈다.
- self-correct에 필요한 이전 실패(코드·traceback)를 agent가 **수동으로** 조회해야 한다 (`cq_dispatch`가 `/evidence` 조회를 노출 안 함).

근본 원인은 TC를 **HTTP REST + CLI wrapper(Bash 실행 + stdout 파싱)** 로 쓰는 것. 폐루프 주체가 LLM agent인 이상, TC 기능을 MCP 도구로 노출하면 추천·환류·적재가 구조화 입출력으로 매끄럽게 흐른다. cq도 `cq mcp`를 제공하니 일관된다.

## 풀고자 하는 문제

Claude Code가 `/loop`로 폐루프를 돌 때:
- **환류 부재**: 이전 실패 traceback을 손으로 httpx 짜서 가져오거나 잊어버려 self-correct가 안 됨.
- **next_config 단절**: 소믈리에가 "lr 이렇게"라고 추천해도 실행·기록에 반영되는 경로가 없음.
- **봉투 보일러플레이트**: agent가 매 적재마다 sha256·integrity·data_ref·contract_version을 직접 조립해야 해 컨텍스트가 오염됨.

## 기존 대안과 차이

| 대안 | 한계 | 우리가 다른 점 |
|------|------|--------------|
| `cq_dispatch.py` CLI (현재) | recommend/run만, 환류 없음. Bash 실행 + stdout JSON 파싱. `--help`로 기능 발견 | MCP 도구로 구조화 입출력, 환류·on-demand 코드 조회 노출 |
| recommend 응답에 환류 포함 | recommend가 더 무거워짐(이미 26s) | 환류를 별도 도구로 분리 — 필요할 때만 호출 |
| 클라가 envelope 조립 (현재 build_envelope) | sha256/integrity/attribution 보일러플레이트가 agent 컨텍스트에 | `tc_ingest_run`이 raw 필드만 받고 서버가 봉투 조립 |

## 요구사항 (EARS)

### 기능 요구사항
- 시스템은 항상 recommend / recent_attempts / get_evidence / ingest_run 을 MCP 도구로 노출한다 (기존 HTTP REST 유지, MCP는 그 위 thin layer).
- WHEN agent가 `tc_ingest_run`을 호출하면 시스템은 raw 필드(code, recipe_id, metrics, config, requirements, lineage_target, branch)로부터 PCQ envelope(content_sha256·integrity·data_ref·contract_version)을 서버에서 조립해 적재한다.
- 시스템은 항상 `tc_ingest_run`의 `attribution.author`를 JWT claim에서 server-derive한다 (클라이언트 위조 불가).
- WHEN `tc_recommend`가 `next_config`를 반환하면 agent가 이를 `tc_ingest_run(config=...)`로 전달하여 PCQ `config`에 기록된다 (hyperparam의 코드 주입 메커니즘은 PCQ 영역으로 분리).
- `tc_recent_attempts`는 `{evidence_id, recipe_id, ok, metrics, stderr_tail}` 요약을 created_at DESC로 반환한다 (modality / recipe_id / failed_only 필터, limit).
- `tc_get_evidence`는 evidence_id로 `pcq.code.content` 본문 포함 전체 evidence를 반환한다 (환류 2단계: 요약 → on-demand 코드).

### 비기능 요구사항
- 신뢰성(RR6): 모든 MCP 도구는 서버 오류·LLM 실패 시에도 폐루프를 중단시키지 않고 명확한 에러를 반환한다.
- 보안: author는 JWT 파생, 시크릿은 .env. MCP 도구가 JWT를 자동 발급.
- 일관성: cq `cq mcp`와 같은 stdio MCP 패턴.

### 범위 외 (Out of Scope)
- cq 코드 디스패치 — `cq mcp`가 유지 (TC MCP 범위 밖).
- 코드 생성 — Claude Code가 직접 (별도 LLM 위임 금지, [[cq-codegen-author-is-claude-code]]).
- hyperparam을 train.py에 *주입*하는 메커니즘 — PCQ 영역(`--config` 규약 등)으로 분리.

## 리스크

| 리스크 | 심각도 | 초기 대응 |
|--------|--------|----------|
| 서버 envelope 조립 시 attribution 출처 모호 | 중 | author를 JWT claim에서 server-derive (위조 차단) |
| MCP 서버 신설 유지 비용 | 낮 | 기존 HTTP/서비스 레이어를 감싸는 thin FastMCP, 로직 중복 최소화 |
| recent_attempts 요약만으로 self-correct 부족 | 낮 | tc_get_evidence on-demand 코드 본문으로 2단계 보강 |
| recommend 26s 지연이 도구 호출에도 그대로 | 중 | 배치 prior 최적화는 적용됨(125→26s), grounding AFC 제한은 후속 |

## 탐구 중 발견한 인사이트

- 환류 재료(이전 코드 본문 + 실패 traceback)는 `GET /evidence`에 **이미 다 있다** — 빠진 건 서버가 아니라 agent가 그걸 집는 손(cq_dispatch가 노출 안 함).
- next_config 문제와 PCQ config 빈약은 같은 뿌리: hyperparam이 코드 본문에 갇힘. `tc_ingest_run(config=...)`로 config가 한 곳으로 흐르면 추천→기록이 이어진다.
- 봉투 조립을 서버로 옮기는 게 가장 큰 agent 이득 — sha256/integrity가 컨텍스트에서 사라진다.
